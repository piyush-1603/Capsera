## 1. Executive Summary & Module Scope

As Member 3, I own the complete assessment and learning evaluation lifecycle:
1. **Assessments (Quizzes/Exams):** Trainer creation, configuration (duration, attempts, deadline, passing threshold), publishing, and deletion.
2. **MCQ Questions:** Question bank authoring (4 options A–D, correct answer key, explanations, points weight, sort ordering).
3. **Attempts Lifecycle:** Trainee attempt initiation, countdown timers, server-enforced attempt limits, and deadline validation.
4. **Auto-Grading Engine:** Server-side scoring in atomic database transactions, answer correctness evaluation, percentage computation, and pass/fail determination without exposing answer keys to trainees before submission.
5. **Results & Analytics:** Trainee scorecards and trainer aggregated course assessment performance reports.
6. **Course Feedback:** Trainee 1–5 star ratings and reviews, with upsert semantics and course-level aggregation.

## 3. Discovered Document & Architecture Inconsistencies

During Step 0 inspection, the following gaps and discrepancies were identified:

1. **API Contract Prefix Discrepancy:**
   * [`docs/API_CONTRACT.md`](file:///Users/piyush/Projects/Capsera/docs/API_CONTRACT.md) Section 3 states `Base Path: /api`.
   * However, `server/src/app.js` line 27, `docs/PRD.md` Section 10.1, and `docs/DECISIONS.md` DR-003 establish `/api/v1` as the canonical prefix.
   * **Resolution:** All endpoints must be mounted and called under `/api/v1`.
2. **Missing Attempt Review Endpoint (Coordination Item):**
   * `API_CONTRACT.md` lists `POST /attempts/:attemptId/submit` and `GET /attempts/me`, but omits `GET /attempts/:attemptId` for inspecting a specific graded scorecard after submission.
   * PRD §6.5 requires: *"After submission, the trainee sees their score, percentage, pass/fail status, and permitted review information."*
   * **Coordination Action:** Propose adding `GET /api/v1/attempts/:attemptId` to the shared `docs/API_CONTRACT.md` and align with Members 1 & 2 before treating it as canonical.
3. **Assessment Modification Locking (Coordination Item):**
   * DECISIONS.md DR-015 dictates that once an assessment has recorded attempts, structural scoring fields (`points`, `correct_option`, `pass_threshold`, adding/removing questions) are locked.
   * **Coordination Action:** Confirm with the team that HTTP `422` with code `ASSESSMENT_LOCKED` is the agreed response before final contract lock.
4. **Data Sanitization for Trainee Questions:**
   * `API_CONTRACT.md` lists `GET /assessments/:assessmentId/questions` with `Roles: Varies`.
   * PRD §6.5 & §8.1 strictly mandate: *"Correct answers and answer-key metadata are not returned in the initial trainee assessment payload."*
   * **Resolution:** When called by a `TRAINEE` (or during an active attempt), the service must explicitly exclude `correct_option` and `explanation`. Only course owners (`TRAINER`) and `ADMIN` can retrieve full answer keys.

### 4.1 Interface Contract with Member 1 (Auth & Permissions)
* **What Member 3 Needs:**
  * `req.user.id` (integer user ID)
  * `req.user.role` (`'TRAINEE'`, `'TRAINER'`, `'ADMIN'`)
  * `req.user.status` (`'ACTIVE'`)
* **Production Isolation Rule:**
  * **Production routes in `server/src/modules/` must NEVER import or mount mock authentication.**
  * In production, routes will depend on Member 1's authenticating middleware to populate `req.user`.
  * If Member 1's middleware is not yet in place when routes are mounted, routes will use an auth placeholder that expects `req.user` or returns `401 UNAUTHORIZED`.
  * The mock auth helper (`server/tests/helpers/authMock.js`) will **only** ever be imported inside `server/tests/` suites to inject mock user identities for test isolation.

### 4.2 Interface Contract with Member 2 (Courses & Enrollments)
* **What Member 3 Needs:**
  * **Course Ownership Check:** Query `courses` table: `SELECT id, trainer_id, status FROM courses WHERE id = $1`. Verify `course.trainer_id === req.user.id` (or user is `ADMIN`).
  * **Course Published Check:** Verify `course.status === 'PUBLISHED'` before trainees can start an attempt.
  * **Enrollment Check:** Query `enrollments` table: `SELECT id, status FROM enrollments WHERE course_id = $1 AND trainee_id = $2 AND status = 'ACTIVE'`.
* **Current Status:** Member 2 has not implemented course endpoints yet, but the `courses` and `enrollments` PostgreSQL tables exist in the database.
* **Member 3 Boundary Rule:** Member 3 queries `courses` and `enrollments` via parameterized read-only SQL queries to verify permissions. Member 3 does **not** create course management or enrollment routes.

## 7. Auto-Grading Transaction Architecture

The auto-grading submission (`POST /api/v1/attempts/:attemptId/submit`) is critical to system integrity:

```sql
BEGIN;

-- 1. Lock attempt row to prevent concurrent duplicate submissions
SELECT id, assessment_id, trainee_id, status, started_at 
FROM assessment_attempts 
WHERE id = $1 FOR UPDATE;

-- Validate: status must be 'IN_PROGRESS'
-- Validate: duration_minutes deadline check (if configured)

-- 2. Fetch all questions with points and correct_option
SELECT id, correct_option, points 
FROM questions 
WHERE assessment_id = $attempt.assessment_id;

-- 3. Calculate score server-side:
-- For each submitted answer:
--   is_correct = (selected_option == question.correct_option)
--   points_awarded = is_correct ? question.points : 0.00
-- Insert batch into attempt_answers with composite assessment_id

-- 4. Calculate total score and percentage
-- percentage = (earned_score / total_possible_points) * 100
-- passed = percentage >= assessment.pass_threshold

-- 5. Update assessment_attempts
UPDATE assessment_attempts SET
  status = 'GRADED',
  score = $earned_score,
  total_points = $total_possible_points,
  percentage = $percentage,
  passed = $passed,
  submitted_at = CURRENT_TIMESTAMP,
  graded_at = CURRENT_TIMESTAMP
WHERE id = $1;

COMMIT;
```

## 8. Incremental Test Strategy

Tests will be developed **incrementally alongside each implementation step** rather than postponed until the end. Tests use Vitest + Supertest in `server/tests/`:

* **Step 1 Tests (`server/tests/validation.test.js`):**
  * Validate assessment payload limits (`pass_threshold` < 0, > 100, `duration_minutes` < 1).
  * Validate question payload (options A–D, valid `correct_option` A–D, `points` >= 1).
  * Validate feedback payload (`rating` 1–5).
  * Test role and ownership guards against simulated user objects.

* **Step 2 Tests (`server/tests/assessments.test.js`):**
  * Trainer creates, updates, and deletes draft assessments.
  * Adding and updating questions with options A–D.
  * DR-015 check: attempt lock stops structural changes when attempts exist.
  * Unauthorized checks: unauthenticated (401), non-owner trainer (403), trainee attempting creation (403).

* **Step 3 Tests (`server/tests/attempts.test.js`):**
  * Enrolled trainee starts attempt on published assessment.
  * Sanitization check: question delivery payload does NOT contain `correct_option` or `explanation`.
  * Attempt cap enforcement: attempt number exceeding `max_attempts` returns 422.
  * Enrollment check: unenrolled trainee cannot start attempt (403).

* **Step 4 Tests (`server/tests/grading.test.js`):**
  * Trainee submits answers; transaction grades answers correctly.
  * Verify `score`, `total_points`, `percentage`, and `passed` calculations.
  * Attempt row status transitions from `IN_PROGRESS` to `GRADED`.
  * Concurrent submit / double submit prevention (submitting already-graded attempt returns error).

* **Step 5 Tests (`server/tests/feedback.test.js`):**
  * Enrolled trainee posts rating and review.
  * Upsert verification: submitting second review updates existing entry.
  * Public review retrieval and course aggregate rating calculations.
  * Unenrolled trainee review rejected (403).
